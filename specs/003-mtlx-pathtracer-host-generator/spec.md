# Feature Specification: MaterialX Pathtracer Host Generator

**Feature Branch**: `003-mtlx-pathtracer-host-generator`

**Created**: 2026-08-24

**Status**: Draft

**Input**: User description: "Create a new Speckit chantier for a MaterialX pathtracer host generator. Add `glsl/pathtracing/mtlx/` with at minimum a copy of `glsl/pathtracing/legacy/pathtracer.glsl`. Generate `evaluateBsdf` and `sampleBsdf` from new C++ code under `D:\WebGL2\MaterialX\MaterialX-rva`, inspired by `EsslHostShaderGenerator` and optionally borrowing implementation ideas from `PathTracerGlslShaderGenerator`, but do not use `PathTracerGlslShaderGenerator` because it is unsuitable. Generation must be based on the code generated for the selected `.mtlx` material model (`open_pbr`, `standard_surface`, `disney`, or other), using MaterialX-provided EDF/BSDF/BRDF/BTDF and not the legacy `_brdf.glsl` or `_btdf.glsl` files under `glsl/pathtracing/legacy`."

### User Story 1 - Create an isolated MTLX pathtracer route (Priority: P1)

As a shader developer, I need a new `glsl/pathtracing/mtlx/` pathtracer route that starts from the current legacy integrator structure but is isolated from legacy BXDF implementation files, so I can evolve the MaterialX-generated path without disturbing the manual legacy comparison path.

**Why this priority**: This creates the working surface for the new generator output and prevents the previous chantier from continuing to mutate the production or legacy comparison path ambiguously.

**Independent Test**: Verify that `glsl/pathtracing/mtlx/pathtracer.glsl` exists, began as a copy of `glsl/pathtracing/legacy/pathtracer.glsl`, and is assembled separately from legacy `_brdf.glsl` and `_btdf.glsl` files.

**Acceptance Scenarios**:

1. **Given** the existing legacy pathtracer, **When** the new chantier setup is completed, **Then** `glsl/pathtracing/mtlx/pathtracer.glsl` exists and contains the pathtracing flow needed to host generated MaterialX dispatch.
2. **Given** the new MTLX pathtracer route, **When** shader assembly is inspected, **Then** it does not include `glsl/pathtracing/legacy/*_brdf.glsl` or `glsl/pathtracing/legacy/*_btdf.glsl`.

---

### User Story 2 - Generate pathtracer BSDF dispatch from C++ (Priority: P2)

As a MaterialX generator developer, I need a new C++ generator in `MaterialX-rva` that emits `evaluateBsdf` and `sampleBsdf` for the pathtracer host, based on the selected MaterialX material graph and generated closure functions.

**Why this priority**: This is the central capability: the pathtracer dispatch methods must be generated by C++ instead of hand-written against legacy OpenPBR-specific BXDF functions.

**Independent Test**: Run the new generator against `D:\WebGL2\MaterialX\materials\open_pbr_carpaint.mtlx` and inspect the emitted GLSL to confirm that it contains generated `evaluateBsdf` and `sampleBsdf` definitions and does not reference legacy `_brdf` or `_btdf` functions.

**Acceptance Scenarios**:

1. **Given** a valid `.mtlx` material using `open_pbr_surface`, **When** the new C++ generator runs, **Then** it emits pathtracer-compatible `evaluateBsdf` and `sampleBsdf` functions wired to MaterialX-generated closure code.
2. **Given** a valid `.mtlx` material using another supported material model such as `standard_surface` or `disney_principled`, **When** the generator runs, **Then** the emitted dispatch is based on that material graph rather than OpenPBR-only legacy functions.
3. **Given** implementation planning for the new generator, **When** C++ inheritance/composition choices are made, **Then** `EsslHostShaderGenerator` is the primary inspiration and `PathTracerGlslShaderGenerator` is not used as the generator class for this chantier.

---

### User Story 3 - Validate generated GLSL in the viewer (Priority: P3)

As a viewer maintainer, I need to load and compile the generated MTLX pathtracer route in the WebGL viewer, so I can validate that generated MaterialX closures replace legacy BXDF dispatch for representative materials.

**Why this priority**: The generator is only useful if the emitted GLSL can be assembled and compiled in the existing viewer runtime.

**Independent Test**: Build the viewer, run a headless pathtracer capture using the MTLX route for `open_pbr_carpaint.mtlx`, and confirm shader compilation succeeds without legacy `_brdf`/`_btdf` includes.

**Acceptance Scenarios**:

1. **Given** generated MTLX pathtracer GLSL for `open_pbr_carpaint.mtlx`, **When** the viewer compiles the shader, **Then** compilation succeeds and the render path reaches `sampleBsdf` and `evaluateBsdf` generated dispatch.
2. **Given** a material whose generated closure contract is missing or incompatible, **When** the viewer attempts to compile or run the MTLX route, **Then** the failure is explicit and does not fallback to legacy BXDF files.

---

### Edge Cases

- The selected `.mtlx` contains a material model whose closures are unsupported by the new pathtracer host generator.
- The selected `.mtlx` graph generates EDF-only, BSDF-only, or mixed closure output.
- The generated code contains helper names that collide with existing pathtracer helpers.
- The generated sampling path cannot provide a physically meaningful PDF for a closure.
- The viewer is asked to use the MTLX route before the generated `evaluateBsdf` and `sampleBsdf` artifact exists.
- A developer accidentally includes legacy `_brdf.glsl` or `_btdf.glsl` in the MTLX route.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST create `glsl/pathtracing/mtlx/` as the dedicated MaterialX-generated pathtracer route.
- **FR-002**: System MUST create `glsl/pathtracing/mtlx/pathtracer.glsl` with at least the contents of `glsl/pathtracing/legacy/pathtracer.glsl` as the initial integration base.
- **FR-003**: System MUST keep `glsl/pathtracing/legacy/` as manual comparison/reference code and MUST NOT make the MTLX route depend on legacy `_brdf.glsl` or `_btdf.glsl` files.
- **FR-004**: System MUST add a new C++ generator under `D:\WebGL2\MaterialX\MaterialX-rva\source\MaterialXGenGlsl` dedicated to emitting pathtracer host dispatch GLSL.
- **FR-005**: The new C++ generator MUST be inspired primarily by `EsslHostShaderGenerator` structure and host-shader responsibilities.
- **FR-006**: The new C++ generator MUST NOT use `PathTracerGlslShaderGenerator` as its implementation class, runtime generator, or required pipeline dependency for this chantier.
- **FR-007**: The new C++ generator MAY reuse small implementation ideas from `PathTracerGlslShaderGenerator` only when copied/adapted deliberately into the new generator and documented as such.
- **FR-008**: The new C++ generator MUST emit a pathtracer-compatible `evaluateBsdf` function whose body is derived from the generated MaterialX material closure graph for the selected `.mtlx`.
- **FR-009**: The new C++ generator MUST emit a pathtracer-compatible `sampleBsdf` function whose body is derived from the generated MaterialX material closure graph for the selected `.mtlx`.
- **FR-010**: Generated dispatch MUST support at least `open_pbr_surface` and MUST be designed to support other MaterialX material models such as `standard_surface`, `disney_principled`, `gltf_pbr`, and `usd_preview_surface` without hard-coding OpenPBR legacy lobe functions.
- **FR-011**: Generated dispatch MUST consume MaterialX-generated EDF/BSDF/BRDF/BTDF/helper functions rather than `glsl/pathtracing/legacy/*_brdf.glsl` or `glsl/pathtracing/legacy/*_btdf.glsl`.
- **FR-012**: System MUST produce a generated GLSL artifact for `D:\WebGL2\MaterialX\materials\open_pbr_carpaint.mtlx` as the first validation material.
- **FR-013**: Viewer integration MUST provide a way to assemble and compile the MTLX pathtracer route separately from both the current generated-WASM route and the legacy comparison route.
- **FR-014**: Missing generated closures, unsupported material models, or incompatible signatures MUST fail explicitly with diagnostics and MUST NOT fallback to legacy BXDF implementation files.
- **FR-015**: Documentation MUST describe how to run the new generator, where generated GLSL artifacts are written, and how to validate that no legacy `_brdf`/`_btdf` dependency remains.

### Key Entities *(include if feature involves data)*

- **MtlxPathtracerRoute**: The new viewer-side GLSL route under `glsl/pathtracing/mtlx/`, including its pathtracer host file and generated dispatch inclusion points.
- **MtlxPathtracerHostGenerator**: The new C++ generator in `MaterialX-rva` responsible for emitting pathtracer host dispatch GLSL.
- **GeneratedBsdfDispatch**: The emitted `evaluateBsdf` and `sampleBsdf` GLSL definitions plus their required closure/helper dependencies.
- **MaterialModelAdapter**: Model-specific mapping from MaterialX generated closure output to the pathtracer dispatch contract.
- **GenerationValidationArtifact**: Output GLSL and report artifacts proving generation, absence of legacy dependencies, and viewer compile readiness.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `glsl/pathtracing/mtlx/pathtracer.glsl` exists and can be diffed against the legacy source to prove the initial copy base.
- **SC-002**: A generated artifact for `open_pbr_carpaint.mtlx` contains `evaluateBsdf` and `sampleBsdf` definitions emitted by the new generator.
- **SC-003**: Automated text checks find zero references from the MTLX route/generated artifact to `glsl/pathtracing/legacy/*_brdf.glsl`, `glsl/pathtracing/legacy/*_btdf.glsl`, or legacy lobe implementation entrypoints.
- **SC-004**: Automated text checks find zero implementation dependency on `PathTracerGlslShaderGenerator` in the new generator build path, except for explicitly documented comparison/reference comments.
- **SC-005**: The viewer production build succeeds after adding the MTLX route.
- **SC-006**: A headless render or shader compile validation for `open_pbr_carpaint.mtlx` completes without falling back to legacy BXDF files.

## Assumptions

- The first validation material is `D:\WebGL2\MaterialX\materials\open_pbr_carpaint.mtlx`.
- The viewer repository remains `D:\WebGL2\MaterialX\OpenPBR-viewer-rva` and the generator repository remains `D:\WebGL2\MaterialX\MaterialX-rva`.
- The new route may initially target one material at a time, provided the generator design is not hard-coded to OpenPBR legacy functions.
- Legacy pathtracer files remain available for visual/reference comparison only.
